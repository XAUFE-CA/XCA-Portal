# 统一身份与应用会话

Status: adopted

## 背景

门户、XCA-OJ、移动应用和管理后台需要识别同一账户，但各自的业务记录、权限和会话不相同。共享数据库、Cookie 或会话凭证会使客户端依赖门户内部实现，不能提供可靠的撤销边界。

## 决策

XCA Identity 是现有 Go 模块化单体内的身份职责，不要求新仓库或独立部署。身份认证、会话存储与撤销、门户自有 HTTP 适配和未来 OIDC 协议适配保持分离。终端只是门户认证入口，应用级认证客户端不依赖终端。

`users.id` 是内部稳定身份标识，邮箱、登录名和显示名均不是跨应用主体标识。未来 OIDC `sub` 在确定的 Issuer 作用域内从内部身份派生或映射；公开稳定主体或按客户端区分的主体留待协议设计决定，不要求客户端直接使用数据库 UUID。

门户使用同源接口与 Host-only Cookie。一个账户可以拥有多个互相独立的门户会话，当前门户注销仅撤销当前会话。账户停用使全部会话无法通过身份校验；退出所有设备与跨应用单点退出需要独立的用户意图和服务端设计。

统一身份、单点登录、客户端登录状态同步和单点退出不是同一能力。当前门户会话不代表 XCA-OJ 已接入单点登录，也不能证明 XCA-OJ 已退出。同源标签页只广播状态可能变化的通知，收到通知后重新查询服务端。

## 后续协议与取舍

XCA-OJ 将作为独立客户端维护业务用户、权限、记录和本地会话。后续采用 OIDC Authorization Code Flow 与 PKCE S256，使用顶层授权跳转，避免依赖第三方 Cookie。客户端根据经验证的 Issuer 和主体标识建立或关联本地账户，不根据用户自行填写的邮箱、登录名或前端身份建立登录状态。正式对接时核验 Hydro 的实际认证扩展点和兼容方式。

正式 OIDC 设计必须确定稳定 Issuer、严格注册的 Redirect URI、`state` 和 `nonce` 校验、短时一次性授权码、客户端类型对应的安全要求、ID Token 校验、JWKS 发布和密钥轮换。跨应用退出另行设计 OIDC Logout 或受控 Back-Channel Logout。身份提供方的部署来源和 Cookie 作用域尚待确定，不预设生产域名，也不通过跨域读取门户数据库或 Cookie 实现认证。

本决策不提供授权端点、令牌端点、发现文档、JWKS、客户端注册、刷新令牌或 OIDC 注销协议。上述能力须在对应设计、实现和验证完成后才能对外宣称可用。
