## 决策结果

第一阶段只实现认证完整流程，采用绑定邮箱的邀请制，不开放自由注册或申请审核流程。Go 服务使用模块化单体和 PostgreSQL，放在当前仓库的 `backend/`，不拆微服务，暂不引入 Redis。

账户只维护一套 `users`。邮箱 OTP、Passkey 和学校统一身份认证都是账户的认证方式，不分别建立用户体系。邀请只授予门户账户激活资格，不作为 XCA 成员资格凭证。学校统一身份认证成功同样不等于自动取得 XCA 成员资格，成员认定规则在对应功能计划中另行确定。

实施顺序调整为：

1. 1A：邀请、邮箱 OTP、门户会话及终端接入。
2. 1B：Passkey 绑定与登录。
3. 1C：学校统一身份认证，等待学校侧应用注册和联调条件。

学校侧尚未联系。学校统一身份认证不作为 1A 的依赖。

本计划不修改 [根工作规范](../../../AGENTS.md) 的当前项目范围。开始 1A 实现时，必须在同一变更中调整“当前只提供公开内容、不引入登录后端和独立 API 服务”的限制，并同步现行架构文档。

## 第一阶段范围

### 试运行目标

1A 以内部认证试运行为验收范围，验证邀请激活、邮箱登录、终端身份展示及会话恢复。登录不增加公开页面的访问权限，也不宣称提供成员专属功能。

登录后要承接的首个业务用途尚未确定。面向成员公开推广前，必须确认该用途、所需身份信息及访问限制，再建立对应功能计划；不通过增加未定义的角色、资料字段或受限页面代替产品决策。

**实施门槛分两级。** 内部 1A 试运行只证明账户激活、登录与会话可用，不将“登录成功”解释为 XCA 成员资格或受保护业务权限。对外开放前，应先由学社确定首个需登录业务（如活动报名、成员资料或投稿中的一个）、业务负责人、准入规则、数据最小集与权限检查点；未作出决策时不提前创建角色表、报名表或后台页面。后续有非终端使用场景时，提供常规登录界面并复用同一个客户端认证服务，而不是让 Terminal 成为唯一身份入口。

## 服务结构

Nuxt 继续负责页面、SSR、终端解释、主题、语言和动画。Go 负责账户、邀请、认证和会话。浏览器终端继续使用现有白名单解释器，不增加通用 `/terminal/execute` 接口。

浏览器只访问同源 `/api/`，避免把跨域资源共享作为默认依赖。Nuxt 服务端转发 `/api/v1/` 到 Go，上游地址仅由服务端运行时配置注入。开发、测试预览和生产均保持同源；静态产物没有进程内转发能力，必须以边缘重写为前提，不作为 1A 的部署形态。终端命令不保存服务地址或凭据。

Go 服务放在当前仓库的 `backend/`，使用独立的 `go.mod`、构建和部署流程。门户与后端的接口、适配器和对应测试在同一变更中审查。只有确认多个客户端或独立维护团队需要后，再评估拆分仓库。

CI 现状是 `quality.yml`：门禁与生产构建在同一个作业内完成并上传产物，浏览器作业按八个分片复用该产物；`cinematic.yml` 与 `images.yml` 按需运行，三者固定共享库提交。`quality.yml` 的 `paths-ignore` 只排除特定过程材料与文档，`backend/**` 和工作流文件不在排除范围。加入 `backend/` 时新增独立作业运行 Go 检查，不把 Go 命令塞进 `scripts/gates/run-gates.ts`，该入口只聚合门户门禁。Go 版本在 `go.mod` 声明，CI 由 `setup-go` 读取。新增作业不会自动成为必需检查，需要在仓库设置中手动加入，并核验路径过滤对 required checks 的影响。

CI 命令入口已统一到清单脚本：`quality.yml`、`cinematic.yml` 和 `images.yml` 分别调用 `bun run test:ci`、`bun run test:scene:ci` 与 `bun run test:visual:ci`，脚本路径与命令名由 `check:references` 校验。旧脚本路径已修复，不再列为后端新任务。认证实施前仍须以实际 CI 运行结果验证，不以本地门禁通过代替远端工作流通过。

门户门禁的范围限于门户：`scripts/gates/check-budgets.ts` 统计 ts、js、vue、css、md，`scripts/gates/check-architecture.ts` 只扫描 `app/**`。实施时确定 Go 侧的对应检查（gofmt、go vet、staticcheck、`go test -race` 与生产构建），并决定是否把阈值或架构规则扩展到 `.go`；不扩展时在[工程质量规则](../../../docs/architecture/engineering-quality.md)写明理由，避免两端规则不一致。

门户门禁由 `scripts/gates/run-gates.ts` 聚合，已包含 `check:tests` 的注册表双向检查。`scripts/gates/check-test-registry.ts` 检查 TypeScript 测试与浏览器测试；Go 的 `*_test.go` 单独由 Go CI 检查，不强行登记为 Bun 或 Playwright 用例。

接口定义或两端接入的改动同时运行门户检查、Go 检查与认证 E2E。共享工作流变更覆盖其影响的范围，路径筛选不得让必要检查缺席。

`backend/` 内部保持以下职责划分，不提前创建空目录：

```text
cmd/api/                  API 进程入口
cmd/xcactl/               邀请管理命令
internal/config/          环境配置读取与校验
internal/httpapi/         HTTP 路由、中间件和错误响应
internal/auth/            OTP、邀请激活和会话用例
internal/identity/        用户查询和状态规则
internal/mail/            邮件发送接口与实际投递实现
internal/store/postgres/  PostgreSQL 查询与事务
migrations/               数据库迁移
api/openapi.yaml          HTTP 接口、字段和错误码
```

HTTP 层只处理请求、响应和身份上下文。认证规则放在应用用例中，数据库事务不泄漏到终端适配器。只有实际存在多个实现或测试替换需求时才定义接口，不为每个结构体机械增加抽象层。

### 飞书邮箱 SMTP 接入候选

- 1A 内部试运行可使用已有飞书邮箱 `me@shenshijun.space` 发信；该地址属于个人身份，不默认为 XCA 的正式系统发件地址。对外开放前优先评估组织控制的飞书公共邮箱，确认邮箱地址、授权成员、DNS、SMTP 权限及回信管理。未创建公共邮箱前不把假定的地址写入配置。
- 飞书官方配置为 `smtp.feishu.cn:465`，使用隐式 TLS（连接建立后立即握手），第三方客户端专用密码须由飞书管理员启用相关权限后在桌面客户端生成；不得使用飞书账号的普通登录密码。保留 `587` + STARTTLS 为通过实际验证后的备选，不自动回退到明文连接。参考 [飞书 SMTP 配置](https://www.feishu.cn/hc/zh-CN/articles/902478147400-%E5%9C%A8%E7%AC%AC%E4%B8%89%E6%96%B9%E9%82%AE%E7%AE%B1%E5%AE%A2%E6%88%B7%E7%AB%AF%E7%99%BB%E5%BD%95%E9%A3%9E%E4%B9%A6%E9%82%AE%E7%AE%B1)。
- SMTP 作为 `internal/mail/` 的可替换传输实现，配置分别包含主机、端口、TLS 模式、用户名、专用密码及发件地址，敏感配置只由运行环境注入。验证码服务不依赖飞书特定协议，测试环境保持测试投递实现。
- 腾讯云默认限制出站 TCP 25 端口，官方提供第三方 SMTP 465 端口使用说明；这不构成实际服务器已可连通的证据。部署时在目标服务器验证出站 465、TLS 证书、SMTP 鉴权、发件人匹配、外部邮箱收信及退信，再允许真实 OTP 流量。参考 [腾讯云 465 端口发信说明](https://cloud.tencent.com/document/product/213/106640)。
- 飞书邮箱存在按版本和认证状态区分的单邮箱、企业总量及外部收件人数限制；实际额度和自动化验证码使用政策须由管理员核实并通过小规模试运行验收。额度不足或正式发信身份不可用时更换邮件服务商，不改变身份认证流程。参考 [飞书发信限制](https://www.feishu.cn/hc/zh-CN/articles/329462350714-%E5%8F%91%E4%BF%A1%E9%99%90%E5%88%B6%E8%A7%84%E5%88%99%E4%BB%8B%E7%BB%8D)。

## 数据设计

1A 使用五类表。除账户、邀请、验证码和会话外，增加 PostgreSQL 原子限流计数，不引入 Redis。字段类型和索引在迁移中明确，内部用户标识不采用学号、邮箱或显示名。

| 表 | 主要字段与规则 |
| --- | --- |
| `users` | 内部 ID、规范化邮箱、唯一登录名、显示名、状态、创建和更新时间；邮箱与登录名分别唯一 |
| `invitations` | 邀请摘要、规范化邮箱、预设登录名、预设显示名、有效期、创建时间、撤销时间、使用时间、使用账户；原始邀请字符串只向创建者显示一次 |
| `email_challenges` | 流程 ID、目标邮箱、OTP 摘要、关联邀请、有效期、尝试次数、使用时间、创建时间；验证成功后失效 |
| `sessions` | 会话摘要、用户 ID、创建时间、最后使用时间、过期时间、撤销时间；数据库不保存浏览器持有的原始会话凭证 |
| `auth_rate_limits` | 限流范围、来源摘要、时间窗、原子计数和过期时间；唯一约束保护同一主体与时间窗的并发更新 |

邮箱统一做大小写和空白规范化，显示用邮箱与登录标识分开处理。账户状态至少区分正常和停用；停用账户不能建立新会话，已有会话在查询时拒绝。

1A 由管理员创建邀请时指定唯一登录名和显示名，激活时写入 `users`，用户不在登录流程中编辑资料。登录名不从邮箱或学号推导，使用适合终端提示身份的受限字符，并保留 `guest` 等系统名称。创建邀请时检查与现有账户及有效未使用邀请的登录名冲突，激活事务仍以数据库约束处理并发冲突。字符集、长度和显示名校验写入接口定义及管理命令测试。

邀请激活和会话建立在同一事务中完成。并发使用同一邀请或同一 OTP 时，最多一个请求成功。撤销邀请不影响已激活账户，停用账户与撤销会话是两个独立操作。

1B 新增 `passkey_credentials`，1C 新增外部身份绑定表。1A 不提前创建角色、成员资料或外部身份空表。

## 1A HTTP 接口

接口统一位于 `/api/v1/`，请求和响应使用 JSON。除健康检查外，不新增与认证无关的资源接口。

| 方法与路径 | 用途 | 成功结果 |
| --- | --- | --- |
| `POST /api/v1/auth/email/code` | 为已有账户或有效邀请申请 OTP | `202`，返回流程 ID 和过期时间 |
| `POST /api/v1/auth/email/verify` | 校验 OTP，必要时激活邀请并建立会话 | `200`，返回身份并设置会话 Cookie |
| `GET /api/v1/auth/session` | 查询浏览器当前会话 | `200`，返回身份或空身份 |
| `POST /api/v1/auth/logout` | 撤销当前会话 | `204`，清除会话 Cookie |
| `GET /healthz` | 进程存活检查 | `200` |
| `GET /readyz` | 数据库等运行依赖检查 | `200` 或 `503` |

申请 OTP 的请求包含邮箱，可选包含邀请字符串。界面由用户选择已有账户登录或邀请激活，不通过查询邮箱探测账户状态。服务端为受邀新用户和已有账户生成真实投递流程；对不能登录的输入返回同样的 `202`、不可预测流程 ID 和有效期格式，且该流程不能通过验证。流程 ID 绑定本次邮箱、邀请和 OTP，验证请求只提交流程 ID 与 OTP，不重新提交邮箱。

身份响应只包含门户展示字段，不作为跨应用主体标识：

```json
{
  "identity": {
    "user": "member-name",
    "label": "成员显示名"
  }
}
```

游客查询返回 `"identity": null`，不把未登录当作服务器错误。`AuthIdentity.user` 对应登录名，`label` 对应显示名；二者均可变。接口不返回账户状态、邮箱、数据库 ID 或其他成员资料。稳定主体及 Issuer 的约束见 [统一身份决策](../../../docs/adr/0002-unified-identity.md)。

公开错误按流程阶段限定，不直接把内部失败原因作为机器码返回：

| 阶段 | 公开响应规则 |
| --- | --- |
| OTP 申请 | 语法有效且未触发限流的请求统一返回 `202`，提示“若符合登录条件，将收到验证码”；账户不存在、停用、邀请无效及单个邮箱投递失败不改变该结果 |
| OTP 验证 | 流程不存在、验证码错误或过期、邀请失效及账户不可用统一返回 `invalid_or_expired_code`，使用相同 HTTP 状态及提示；不公开 `invalid_invitation` 或 `account_disabled` |
| 请求校验与限流 | 可返回 `invalid_request` 或 `rate_limited`；语法校验和邮箱、来源地址计数不依赖账户是否存在，重试信息规则保持一致 |
| 全局服务故障 | 数据库或邮件服务整体不可用时可返回可重试的 `service_unavailable`，判定独立于目标邮箱，不把单个收件人的投递失败映射为全局故障 |
| 会话查询与注销 | 无会话或已失效会话分别返回空身份及幂等注销结果；网络和服务错误不得伪装为空身份或注销成功 |

响应检查同时覆盖 HTTP 状态、字段、有效期、重试信息和处理时间差异，不只比较 JSON 结构。具体错误、过期、停用、邀请及邮件投递原因只记录在受控日志中。门户把公开机器码映射为双语文案，终端不直接展示数据库、邮件服务商或网络堆栈错误。规则依据参考 [OWASP 认证指南](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html#authentication-and-error-messages)。

接口文档与实现同步维护。前端从同一响应定义映射 TypeScript 类型，不另写一份无校验的重复字段清单。

### 接口定义与兼容检查

`backend/api/openapi.yaml` 是 1A HTTP 请求、成功响应、公开错误、状态码和会话 Cookie 的唯一接口定义。实施前先描述全部六个端点，包括 `202` 的假流程与真实流程同形响应、`identity: null`、`204` 空正文、错误响应与 `Set-Cookie`。健康检查是否经过公共 `/api` 代理由部署决定，不将进程内部探针无条件暴露给浏览器。

- 从 OpenAPI 生成前端 TypeScript 类型，或通过受测试的转换工具保持类型一致，不在终端适配器手工维护第二套响应字段。
- 在 CI 校验 OpenAPI 语法与引用、生成产物是否过期，并用 Go HTTP 集成测试验证实际状态码、响应体、响应头、错误字段与文档一致。类型生成不能替代 Go 运行时的接口校验。
- 定义 `/api/v1/` 的兼容规则：现有字段的含义和身份状态不能静默变化；破坏性更改需明确迁移消费者。前端须区分请求失败、无会话与已认证三种结果，不把网络异常解析为游客身份。
- 仅认证接口接入时使用同源 `/api`，不新增第二个 Nuxt 服务端身份 API 或在浏览器硬编码 Go 上游地址。

## 会话与请求安全

- 浏览器持有密码学随机会话凭证，数据库只保存其摘要。会话凭证不出现在 JSON、终端输出、URL 或日志中。
- Cookie 使用 `Secure`、`HttpOnly`、合适的 `SameSite` 和受限路径；正式环境不通过 JavaScript 读取会话。
- 会话采用明确的绝对有效期。注销、账户停用和管理员撤销后，`GET /auth/session` 必须返回空身份。
- 注销及其他已认证写请求要求跨站请求伪造防护。OTP 申请与验证通过同源检查、服务端流程 ID 和限流防止跨站提交及验证码猜测。
- OTP 使用安全随机源生成，只保存摘要，设置有效期、最大尝试次数、重发间隔及按邮箱和来源地址的限流。
- 六位等低熵 OTP 不使用无密钥的快速哈希直接存储。优先采用服务端密钥参与的 HMAC，并绑定不可预测流程 ID，验证码明文不落库；密钥由运行环境安全注入且不得进入日志或仓库。相同邮箱的重新申请、旧流程失效及密钥轮换后的行为在实施时定案并测试。
- 尝试次数、重发间隔和按邮箱、来源地址的限流更新应由 PostgreSQL 事务或等价原子操作保护，多个 Go 进程并发请求仍然生效。仅信任部署代理声明的客户端来源地址，不能直接信任任意用户请求头；超出阈值不泄漏账户是否存在。
- 生产 Cookie 优先评估 `__Host-` 前缀：必须 `Secure`、`Path=/` 且不得设置 `Domain`；`SameSite` 按实际登录及回调路径选定。认证响应设置 `Cache-Control: no-store`，禁止缓存身份或 `Set-Cookie`；不要为了所谓受限路径破坏 `__Host-` 约束。
- 明确同源写请求的 `Origin` 校验、需要额外 CSRF Token 的操作与缺少 `Origin` 时的处理策略。`SameSite`、JSON Content-Type、流程 ID 和限流都不能单独代替完整的 CSRF 防护，验证与注销均应覆盖跨站请求测试。
- 邀请字符串和 OTP 按敏感输入处理，不进入命令历史、普通输入草稿、Transcript、分析事件或访问日志。
- 日志记录请求 ID、稳定错误码和必要安全事件，不记录 Cookie、邀请原文、OTP、邮件正文或完整敏感请求体。
- 数据库查询使用参数化语句。限流和账户状态判断在服务端执行，前端隐藏入口不构成授权。

## 部署、迁移与恢复

1A 不先建立独立 BFF 或微服务。Nuxt 服务端把 `/api/v1/` 转发给 Go；部署层也可在经过验证后承担同源转发。只允许受控代理提供客户端来源信息，不根据任意客户端声明的来源地址作安全判断。代理转发行为与部署要求见 [Go 后端](../../../docs/architecture/backend.md)。

- `/healthz` 只检查进程是否存活；`/readyz` 检查数据库等必需依赖，不在响应中泄漏 DSN、表名或服务商信息。生产探针默认由部署层访问，不经公共代理直接公开。
- 数据库迁移由受控发布步骤在新进程接流量前执行，不让多个 API 实例同时自行运行迁移。迁移具有版本记录与单次执行保护；破坏性变更应先部署兼容读取和写入的版本，备份与恢复步骤经过试运行，不能用“向下迁移”代替数据恢复。
- 环境配置分离开发、测试和生产。数据库连接、邮件投递、OTP HMAC 密钥、会话摘要密钥（如使用）及反向代理信任列表从受控环境注入；每次登录的会话凭证由服务端安全随机生成，绝不从固定环境变量读取。启动时校验缺失配置，日志只记录安全的配置名称与失败原因，不打印值。
- 至少记录请求 ID、HTTP 状态、错误类别、投递与数据库依赖故障及限流事件；敏感输入不进访问日志。就绪失败、邮件服务持续不可用和迁移失败需要明确告警及人工处理人，详细日志保留期限在部署前确定。
- Go 数据库访问先选用标准库 `database/sql` 或 `pgx` 一类直接访问方案；仅在重复查询、模式增长确有收益时评估代码生成。不因分层习惯提前引入完整 ORM、事件总线或空接口。

## 终端接入

新增门户首方认证客户端，应用级身份状态位于 `app/features/auth/`，不依赖终端。终端适配器通过 `TerminalServices.auth` 注入，只负责命令交互，不拥有应用身份。统一身份与未来 OIDC 的决策见 [统一身份与应用会话](../../../docs/adr/0002-unified-identity.md)。

终端保留草稿、历史和视觉提示；认证客户端维护当前标签页的查询状态与待核对标记，Go 会话是身份依据。`error` 不等于 `guest`，组件卸载不清除待核对标记。登录、注销和恢复请求使用单调操作版本，旧响应不得覆盖新操作。同源标签页只发送身份可能变化的通知，并向服务端重新查询。

`login` 的适配流程为：

1. 选择已有账户登录或邀请激活，再询问邮箱；邀请激活在独立敏感输入中提供邀请字符串。
2. 请求 OTP，并通过现有 `ctx.ask()` 的 `otp` 输入读取验证码。
3. 校验成功后返回 `AuthIdentity`，由现有命令调用 `ctx.setIdentity()`。
4. 失败时按[公开错误码到终端输出](#公开错误码到终端输出)返回已本地化的结果，不泄漏邮箱是否存在，不自动重复发送邮件。

`whoami` 通过 `getSession()` 查询真实身份。页面挂载后恢复有效会话，使刷新后的提示身份与 Cookie 一致；应用级客户端也可供普通页面使用。请求必须传递 `AbortSignal`，组件卸载或新命令取消后不得写回旧身份。

`logout` 成功后才清除本地身份和输出。网络失败时不直接清除身份或宣称注销成功，按下文规则重新核对服务端会话。

### 公开错误码到终端输出

`Session` 对 `sensitive` 命令统一把异常映射为 `error.auth`，`login` 已标记为 sensitive。适配器若将 `invalid_or_expired_code`、`rate_limited`、`service_unavailable` 当作异常抛出，会退化为通用失败。1A 改为下文的结构化 `AuthResult`，由命令层翻译预期失败并返回错误行，现有错误行机制设置失败状态。未知程序异常仍使用安全的通用提示；取消继续由 `AbortSignal` 处理。

适配器需要翻译能力来提出双语输入问题，而 `AuthGateway.login` 的上下文当前是 `Pick<CommandContext, "ask" | "write">`。1A 把它扩展为包含 `t` 的上下文，公开错误码由命令层翻译，适配器不重复生成文案。同步修改 `app/features/terminal/core/types.ts`、[终端扩展接口](../../../docs/architecture/terminal-extending.md#多步交互与登录)与 `core/extensions.test.ts`。命令行的历史记录规则不变：`login` 不写入历史与 Transcript。

### 登录超时与取消

当前 `TERMINAL.limits.commandTimeout` 为 30 秒，`Session.execute()` 从命令开始统一计时，包含 `ctx.ask()` 等待输入。接入前必须调整命令的超时策略，不能把收取验证码的人工等待压入同一个 30 秒期限，也不能直接放大所有命令的超时。

改动集中在 `app/features/terminal/config.ts` 的期限配置、`core/session.ts` 的计时与取消，以及 `core/session.test.ts` 的用例。命令通过可选元数据声明自己的期限，`Session` 在等待 `ctx.ask()` 时分段计时；Parser、命令注册与输出归属不变。放大全局期限会让其他命令在挂起时更久不返回，不能采用。

- 普通命令保留现有执行期限。登录分别设置网络请求超时、单步输入等待期限和流程总期限，等待输入不消耗网络请求时限。
- OTP 有效期由服务端执行，不因终端等待、暂停或切换页面延长。客户端在期限内允许取消，并提供明确的过期及重新发起提示，不自动重发邮件。
- Esc、Ctrl+C、超时或卸载取消本地等待和请求，并释放输入。取消后的旧命令不得追加输出或调用 `ctx.setIdentity()`。
- `AbortSignal` 取消浏览器等待不等于回滚服务端事务。验证或注销已经提交时，服务端会话可能与本地身份不同；不能承诺取消后账户未激活或会话未建立。
- 验证或注销请求取消、超时或响应丢失后，将本地认证结果标为待核对。当前有效的生命周期通过新的 `getSession()` 请求恢复身份；组件已卸载时，在下次挂载核对。恢复请求独立于旧命令，只更新身份，不重放欢迎输出、验证、投递或注销。服务端已提交但浏览器未收到会话 Cookie 时，查询仍返回游客，需要重新登录，不重试已消费的 OTP 或撤销已完成的邀请激活。
- 核对失败时保留待核对状态并显示可重试提示。原请求尚未完成时，一次查询不能视为最终结果；后续 `whoami`、新认证操作前或重新挂载时再次核对。恢复结果只能在对应生命周期和认证操作仍有效时应用，不能覆盖较新的登录或注销。

### 生命周期与文案

主题和语言切换不重建终端或应用级认证状态。SSR 不共享可变用户状态，浏览器认证查询由客户端生命周期触发。

双语新增文案遵循[翻译规则](../../../docs/terminology/translation.md)。现有文案在同一变更中改写，中英两份同步：

| 位置 | 当前内容 | 处理 |
| --- | --- | --- |
| `command.loginUnavailable` | 成员登录尚未开放 | 区分服务不可用与功能未开放，或移除 |
| `command.membersUnavailable` | `whoami` 游客分支输出“成员系统尚未开放” | 改为未登录提示，不再声称系统未开放 |
| `summary.login` | 帮助与 `man` 中显示“等待接入后端” | 改为成员登录入口 |

新增公开错误码 `invalid_or_expired_code`、`invalid_request`、`rate_limited`、`service_unavailable` 的双语文案，两份 locale 的 key 与插值保持一致，由 `app/i18n/i18n.test.ts` 校验。

术语先登记再使用。[术语表](../../../docs/terminology/terms.md)目前只有“会话”一条与认证相关，邀请、验证码、账户、统一身份认证与成员资格在写入文档和界面文案前先补表。

### API 结果契约与认证状态

预期失败不使用异常传递，前端统一使用判别联合类型，成功身份与业务失败分别携带明确字段：

```ts
type AuthFailureCode =
  "invalid_request" | "invalid_or_expired_code" | "rate_limited" | "service_unavailable";

type AuthResult<T> =
  { ok: true; value: T } | { ok: false; code: AuthFailureCode; retryAfterSeconds?: number };

// login: AuthResult<AuthIdentity>
// getSession: AuthResult<AuthIdentity | null>
// logout: AuthResult<null>
```

- `getSession` 成功返回空身份才代表游客，网络或服务故障为 `ok: false`，不得调用 `setIdentity(null)`。`logout` 必须收到 `204` 后才能清空身份；超时或结果不确定时标记待核对。`login` 成功才设身份，错误码由命令的 `ctx.t` 翻译并输出带错误样式的行。
- OpenAPI 明确 `400 invalid_request`、`400 invalid_or_expired_code`、`429 rate_limited`、`503 service_unavailable`。非法来源的浏览器写请求使用 `403` 和安全的通用错误，不包含内部状态。网络断开归一化为 `service_unavailable`，取消单独处理，不冒充服务端响应。
- 请求验证码返回的 `202` 统一包含 `flow_id`、`expires_at`，真实和假流程具有同形响应；假流程永远不能验证成功。相同邮箱的再次申请会使旧的未使用挑战失效，不自动重发验证码。
- 应用级认证客户端持有当前标签页的 `unknown/checking/guest/authenticated/error` 状态和单调操作版本。Go 会话 Cookie 是最终身份依据；旧 `whoami`、组件卸载后的响应或已取消请求不得覆盖新登录、注销。客户端不依赖终端或 Intro，重新挂载和标签页失效通知触发核对。

### OTP、会话与命令超时

| 参数 | 1A 内部试运行默认值 |
| --- | --- |
| 邀请有效期 | 7 天 |
| OTP 长度与有效期 | 6 位数字，10 分钟 |
| OTP 错误尝试 | 每流程最多 5 次 |
| 同邮箱重发间隔 | 至少 60 秒 |
| 同邮箱申请额度 | 每 15 分钟最多 3 次 |
| 来源 IP 申请额度 | 每 15 分钟最多 30 次，留意校园 NAT |
| 会话有效期 | 绝对 24 小时，不自动延长 |
| 单个网络请求超时 | 15 秒 |
| OTP 人工输入等待 | 最多 8 分钟，不延长服务端 OTP 有效期 |
| 整个登录流程期限 | 12 分钟，普通终端命令仍为 30 秒 |

- `TerminalSession` 的 `ctx.ask` 已支持随 `AbortSignal` 取消并清理交互，但 `execute` 仍以统一 30 秒计时。为多步命令增加明确的期限元数据，将输入等待、每次网络请求及总流程定时分离；进入和离开输入阶段时更新计时器，不放大普通命令超时。完成、Esc、Ctrl+C、卸载及失败都释放计时器和监听。
- 取消验证码验证或注销不代表回滚已提交的 Go 事务。请求取消、Cookie 响应丢失或旧请求迟到时，用新 `getSession` 查询当前服务器会话；不重放欢迎消息，不自动重试已消费的 OTP。待核对状态持续到有效的新查询完成。
- 生产使用 `__Host-xca_session` Cookie，`Secure; HttpOnly; Path=/; SameSite=Lax`，不允许 `Domain`，通过 HTTPS 同源入口签发。仅本地 HTTP 环境使用不同名称的开发 Cookie，同样保持 `HttpOnly` 和来源校验；不将开发设置用于生产。身份相关响应统一 `Cache-Control: no-store`。
- 浏览器 `POST` 必须带与配置严格一致的 `Origin`，不存在或不匹配都拒绝。只接受 `application/json`，不开跨域凭据 CORS。`SameSite` 不能代替来源检查；反向代理的 `X-Forwarded-*` 仅接受可信代理提供的值。

### 并发数据库与邮件投递

- OTP 使用安全随机源生成。`email_challenges` 存储绑定流程 ID 的服务端密钥 HMAC 和密钥版本，验证时恒定时间比较；旧密钥保留至所有有效挑战过期。明文 OTP、邀请串、会话 Cookie 和 HMAC 密钥均不得记录在日志。会话凭证独立高熵生成，数据库只保存安全摘要。
- `auth_rate_limits` 通过 `(scope, subject_digest, window_start)` 唯一约束及 `INSERT ... ON CONFLICT DO UPDATE ... RETURNING` 原子计数。邮箱与来源 IP 使用单独密钥下的摘要而非原文作为限流主体。挑战校验锁行更新失败次数，并发请求不得越过上限或重复消费验证码。限流数据保留与清理不能提前解除有效限制。
- 真实与假流程共同经过申请限流、流程建立和一致的公开响应。真实邮件在数据库事务提交后交由有界并发的进程内发送器执行，浏览器不等待 SMTP 结果，避免通过投递延迟稳定枚举账户。发送器容量饱和须在账户判定前作为全局服务故障处理，不能按邮箱选择性返回异常。该非持久队列在进程重启时可能丢信，内部试运行依赖限流后的人工重发；面向更大范围开放前须验证可靠性并决定是否采用 PostgreSQL Outbox 或可靠的邮件服务 API。
- 生产 SMTP 采用飞书 `smtp.feishu.cn:465` 隐式 TLS，并验证证书、发件身份和第三方客户端专用密码。本地只连接 Mailpit。真实腾讯云服务器出口、发信额度、授权、备份、恢复和安全日志保留期在部署验收阶段确认。

- HMAC 校验包含流程 ID；存储中不存在可离线穷举的无密钥验证码哈希；重发、旧流程失效、密钥缺失和多实例并发限流具有测试。
- 未受邀邮箱不能激活账户，响应不暴露账户是否存在。
- 已有、未知、停用邮箱及无效邀请的公开响应遵守分阶段规则，覆盖单个邮箱投递失败、全局服务故障及按邮箱限流，比较 HTTP 状态、字段和处理时间差异。
- 会话刷新可恢复，注销和停用后失效，伪造或篡改会话凭证不能通过。
- 邮件投递失败或验证事务回滚时不建立账户或会话。验证事务提交后响应丢失、请求取消或客户端超时，账户和会话仍保持完整。查询结果以浏览器实际持有的有效 Cookie 为准，未收到 Cookie 时返回游客并允许重新登录，不将网络中断视为事务回滚。
- 按 OpenAPI 核对所有接口的实际状态码、响应、错误机器码、Cookie 与缓存头。跨站写请求被拒绝，可信与不可信来源转发头的解析结果不同且符合部署配置。
- 生产中的每个迁移版本只执行一次，旧版本的兼容窗口与失败处理明确；备份可恢复，健康检查不暴露部署秘密。

### 门户验证

- 受邀用户可从 `login` 完成激活，随后 `whoami` 显示后端身份。
- 已有用户可登录、注销，刷新后有效会话仍能恢复。
- 无效邀请、错误 OTP、限流、服务不可用和请求取消均有中英文结果。
- 用户等待验证码超过 30 秒仍可在登录及 OTP 有效期内完成流程，普通命令保留执行期限；单步等待、网络请求及流程总期限分别覆盖超时和清理。
- 覆盖验证或注销提交前后取消、Cookie 设置后响应丢失、原请求晚于恢复查询完成、卸载后重新挂载及旧恢复请求晚于新认证操作返回，身份最终以当前服务端会话为准，不重放旧输出或副作用。
- 验证码错误、验证码过期、限流和服务不可用分别显示对应双语文案，不退化为通用认证失败。
- 常规认证 E2E 使用替身网关且不连接数据库；Go 集成测试单独运行，现有浏览器分片不启动 Go 服务与 PostgreSQL。
- 独立真实链路冒烟测试在同源 `/api/v1/` 下运行 Go、PostgreSQL、Nuxt 和测试收件器，验证邀请激活、已有账户登录、`Set-Cookie` 与跨刷新会话、注销、CSRF 拒绝和上游不可用。Cookie 的 HTTPS 与 `Secure` 语义必须由匹配生产部署的测试入口验证，不能只用 HTTP 本地预览声称已覆盖。
- 敏感输入不进入历史、草稿、Transcript 和日志。
- 主题与语言切换保留会话；终端展开、路由返回和减少动画行为不回归。
- 未登录访问现有公开页面不受影响，现有终端命令与虚拟工作区保持原行为。

门户继续执行 `bun run check`、`bun run check:tests` 与相关 `bun run test:e2e`。测试层级与执行参数以[测试注册表](../../../docs/testing/README.md)为准，CI 的 `system` 分片经 `scripts/tests/test-plan.ts` 执行。Go 检查以 `backend/` 中跨 Windows 与 Linux 可运行的统一入口为准，本地与 CI 调用同一组命令，不以门户构建成功代替 Go 测试。测试邮件投递使用专用测试实现，真实服务商至少进行一次受控验收，不发送自动化批量邮件。

## 1C：学校统一身份认证

学校公开入口为 [西安财经大学统一身份认证](https://cas.xaufe.edu.cn/login)。公开页面可见账号登录和扫码登录，但票据校验端点、返回属性和应用接入要求尚未验证。

实施前取得以下学校侧条件：

- 门户回调地址完成应用注册和白名单配置。
- 确认使用 `/serviceValidate` 还是 `/p3/serviceValidate`。
- 确认稳定身份字段、可用属性和个人信息使用限制。
- 确认扫码登录也能完成标准服务票据流程。

Go 后端直接校验服务票据并核对 `service`，不接受前端提交的学号或姓名。学校身份通过独立外部身份表绑定到 `users`，邀请仍决定是否允许首次激活。服务票据不进入日志。

认证页优先使用新窗口，完成后由同源回调页通知原窗口重新查询会话，避免整页跳转丢失浏览器内存中的终端历史和草稿。通知只包含成功或失败，不包含会话凭证。门户注销默认只撤销门户会话，不主动退出全校统一身份认证。

学校侧条件未满足前，1C 保持未验证状态，不用模拟学校响应宣称接入完成。标准协议核对可参考 [Apereo CAS Protocol Specification](https://apereo.github.io/cas/development/protocol/CAS-Protocol-Specification)。
