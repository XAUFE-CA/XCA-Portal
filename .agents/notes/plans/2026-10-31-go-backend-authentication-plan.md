# Go 后端认证实施计划

Status: proposed

更新日期：2026-11-06。复核 2026-11-04 至 2026-11-06 的终端命令分组、入场模块抽取、CI 分片与主题过渡改动后，更新接入位置与前置决策，不改变后端方案。

本次复核依据：`app/features/terminal/core/session.ts`（统一计时与敏感命令的错误映射）、`app/features/terminal/client-session.ts` 与 `app/components/home/HeroSection.vue`（装配点）、`playwright.config.ts`（单一测试服务器）、`.github/workflows/quality.yml` 与 `scripts/run-gates.ts`（CI 与门禁范围）、`docs/AGENTS.md` 与 `docs/terminology/terms.md`（文档与术语登记）。

## 决策结果

第一阶段只实现认证完整流程，采用绑定邮箱的邀请制，不开放自由注册或申请审核流程。Go 服务使用模块化单体和 PostgreSQL，放在当前仓库的 `backend/`，不拆微服务，暂不引入 Redis。

账户只维护一套 `users`。邮箱 OTP、Passkey 和学校统一身份认证都是账户的认证方式，不分别建立用户体系。邀请只授予门户账户激活资格，不作为 XCA 成员资格凭证。学校统一身份认证成功同样不等于自动取得 XCA 成员资格，成员认定规则在对应功能计划中另行确定。

实施顺序调整为：

1. 1A：邀请、邮箱 OTP、门户会话及终端接入。
2. 1B：Passkey 绑定与登录。
3. 1C：学校统一身份认证，等待学校侧应用注册和联调条件。

学校侧尚未联系。学校统一身份认证不作为 1A 的依赖。

本计划不修改 [根工作规范](../../../AGENTS.md) 的当前项目范围。开始 1A 实现时，必须在同一变更中调整“当前只提供公开内容、不引入登录后端和独立 API 服务”的限制，并同步现行架构文档。

## 第一阶段范围

### 试运行目标

1A 以内部认证试运行为验收范围，验证邀请激活、邮箱登录、终端身份展示及会话恢复。登录不增加公开页面的访问权限，也不宣称提供成员专属功能。

登录后要承接的首个业务用途尚未确定。面向成员公开推广前，必须确认该用途、所需身份信息及访问限制，再建立对应功能计划；不通过增加未定义的角色、资料字段或受限页面代替产品决策。

### 包含

- Go API 进程、PostgreSQL 迁移、配置读取和健康检查。
- 开发服务器与测试预览的同源 `/api` 转发配置，以及生产环境转发位置的接入说明。
- 通过 Go 管理命令创建和撤销邀请，不建设管理后台。
- 受邀用户通过邮箱 OTP 激活账户。
- 已激活用户通过邮箱 OTP 登录。
- 门户会话的建立、查询、刷新恢复、过期和撤销。
- `login`、`logout`、`whoami` 与真实后端连接。
- 中英文错误提示、请求取消、限流和安全日志。
- Go 测试、门户单元测试、接口测试和相关 E2E。

### 不包含

- 自由注册、申请审核、找回密码、用户名密码和管理后台。
- 角色权限系统、成员资料扩展和社区内容。
- 迁移现有 Nuxt Content 正文、首页轮播语句或站点配置。
- 远程 Shell、服务端终端命令执行、服务器文件读取和终端历史保存。
- Passkey 和学校统一身份认证，分别由 1B、1C 处理。
- Redis、消息队列、微服务和独立实时连接服务。

## 服务结构

Nuxt 继续负责页面、SSR、终端解释、主题、语言和动画。Go 负责账户、邀请、认证和会话。浏览器终端继续使用现有白名单解释器，不增加通用 `/terminal/execute` 接口。

浏览器只访问同源 `/api/`，避免把跨域资源共享作为默认依赖。开发服务器与测试预览通过 `nuxt.config.ts` 中的 Nitro 路由规则转发到 Go 服务，上游地址由运行时配置注入，不提交环境文件。开发环境的 4100 端口与 Playwright 的 4102 预览都必须具备该转发，否则 Cookie 作用域与跨站请求伪造的同源检查在本地和 CI 无法验证。生产环境可以沿用同一规则，也可以由部署层反向代理，两种做法都要保持同源。`bun run generate` 的静态产物没有进程内转发能力，必须以边缘重写为前提，不作为 1A 的部署形态。终端命令不保存服务地址或凭据。

Go 服务放在当前仓库的 `backend/`，使用独立的 `go.mod`、构建和部署流程。门户与后端的接口、适配器和对应测试在同一变更中审查。只有确认多个客户端或独立维护团队需要后，再评估拆分仓库。

CI 现状是一个提交触发的工作流 `quality.yml`：门禁与生产构建在同一个作业内完成并上传产物，浏览器作业按八个分片复用该产物；`cinematic.yml` 与 `images.yml` 按需运行，三者各自固定共享库提交，工作流没有路径筛选。加入 `backend/` 时新增独立作业运行 Go 检查，不把 Go 命令塞进 `scripts/run-gates.ts`，该入口只聚合门户门禁。Go 版本只在 `go.mod` 声明，CI 由 `setup-go` 读取。新增作业不会自动成为必需检查，需要在仓库设置中手动加入，并分别核验工作流结果与 required checks 配置。

门户门禁的范围限于门户：`scripts/check-budgets.ts` 统计 ts、js、vue、css、md，`scripts/check-architecture.ts` 只扫描 `app/**`。实施时确定 Go 侧的对应检查（gofmt、go vet、staticcheck、`go test -race` 与生产构建），并决定是否把预算或架构规则扩展到 `.go`；不扩展时在[工程质量规则](../../../docs/architecture/engineering-quality.md)写明理由，避免两端规则不一致。

接口定义或两端接入的改动同时运行门户检查、Go 检查与认证 E2E。共享工作流变更覆盖其影响的范围，路径筛选不得让必要检查缺席。

`backend/` 内部保持以下职责划分，不提前创建空目录：

```text
cmd/api/                  API 进程入口
cmd/xcactl/               邀请管理命令
internal/config/          环境配置读取与校验
internal/httpapi/         HTTP 路由、中间件和错误响应
internal/auth/            OTP、邀请激活和会话用例
internal/identity/        用户查询和状态规则
internal/mail/            邮件发送接口与实际投递实现
internal/store/postgres/  PostgreSQL 查询与事务
migrations/               数据库迁移
api/openapi.yaml          HTTP 接口、字段和错误码
```

HTTP 层只处理请求、响应和身份上下文。认证规则放在应用用例中，数据库事务不泄漏到终端适配器。只有实际存在多个实现或测试替换需求时才定义接口，不为每个结构体机械增加抽象层。

## 1A 前置决策

实现前确认以下事项；未确认项不得通过硬编码或提交环境文件代替：

| 事项 | 需要确定的内容 |
| --- | --- |
| 邮件投递 | 服务商或邮件服务器、发件地址、域名验证、开发环境邮件接收方式 |
| CI 接入 | Go 作业的检查命令与安装方式、接口联动时的运行时机及 required checks 的加入与核验 |
| 部署地址 | 门户与 API 的正式域名、HTTPS、反向代理和 Cookie 作用域 |
| 邀请责任 | 谁有权创建邀请，使用何种受控环境执行管理命令 |
| 安全参数 | OTP 有效期、重发间隔、尝试上限、限流阈值和会话有效期 |
| 交互期限 | 网络请求超时、单步输入等待期限和登录流程总期限，分别与 OTP 有效期协调 |
| 代理位置 | 开发服务器、测试预览与生产环境的同源 `/api` 由哪一层转发；上游地址如何按环境注入；静态产物是否排除在部署形态之外 |
| 后端替身 | 认证 E2E 使用进程内替身网关还是真实 Go 服务；Go 集成测试的 PostgreSQL 获取方式；浏览器分片不承担数据库 |
| 迁移执行 | 生产迁移由谁在何时执行（发布步骤或进程启动）、失败回滚与备份 |
| Go 工具链 | Go 版本、CI 安装方式与静态检查工具；预算和架构检查是否覆盖 `.go` |

开发环境使用可检查的邮件接收工具或测试投递器，不把真实邮件凭据写入仓库。生产投递失败使对应 OTP 流程不可验证，并记录投递失败及内部原因，不记录邮件正文和 OTP。面向浏览器的结果遵循下文的分阶段错误规则，不因单个邮箱的投递失败暴露账户是否存在。

## 数据设计

1A 使用四类表。字段类型和索引在迁移中明确，内部用户标识不采用学号、邮箱或显示名。

| 表 | 主要字段与规则 |
| --- | --- |
| `users` | 内部 ID、规范化邮箱、唯一登录名、显示名、状态、创建和更新时间；邮箱与登录名分别唯一 |
| `invitations` | 邀请摘要、规范化邮箱、预设登录名、预设显示名、有效期、创建时间、撤销时间、使用时间、使用账户；原始邀请字符串只向创建者显示一次 |
| `email_challenges` | 流程 ID、目标邮箱、OTP 摘要、关联邀请、有效期、尝试次数、使用时间、创建时间；验证成功后失效 |
| `sessions` | 会话摘要、用户 ID、创建时间、最后使用时间、过期时间、撤销时间；数据库不保存浏览器持有的原始会话凭证 |

邮箱统一做大小写和空白规范化，显示用邮箱与登录标识分开处理。账户状态至少区分正常和停用；停用账户不能建立新会话，已有会话在查询时拒绝。

1A 由管理员创建邀请时指定唯一登录名和显示名，激活时写入 `users`，用户不在登录流程中编辑资料。登录名不从邮箱或学号推导，使用适合终端提示身份的受限字符，并保留 `guest` 等系统名称。创建邀请时检查与现有账户及有效未使用邀请的登录名冲突，激活事务仍以数据库约束处理并发冲突。字符集、长度和显示名校验写入接口定义及管理命令测试。

邀请激活和会话建立在同一事务中完成。并发使用同一邀请或同一 OTP 时，最多一个请求成功。撤销邀请不影响已激活账户，停用账户与撤销会话是两个独立操作。

1B 新增 `passkey_credentials`，1C 新增外部身份绑定表。1A 不提前创建角色、成员资料或外部身份空表。

## 1A HTTP 接口

接口统一位于 `/api/v1/`，请求和响应使用 JSON。除健康检查外，不新增与认证无关的资源接口。

| 方法与路径 | 用途 | 成功结果 |
| --- | --- | --- |
| `POST /api/v1/auth/email/code` | 为已有账户或有效邀请申请 OTP | `202`，返回流程 ID 和过期时间 |
| `POST /api/v1/auth/email/verify` | 校验 OTP，必要时激活邀请并建立会话 | `200`，返回身份并设置会话 Cookie |
| `GET /api/v1/auth/session` | 查询浏览器当前会话 | `200`，返回身份或空身份 |
| `POST /api/v1/auth/logout` | 撤销当前会话 | `204`，清除会话 Cookie |
| `GET /healthz` | 进程存活检查 | `200` |
| `GET /readyz` | 数据库等运行依赖检查 | `200` 或 `503` |

申请 OTP 的请求包含邮箱，可选包含邀请字符串。界面由用户选择已有账户登录或邀请激活，不通过查询邮箱探测账户状态。服务端为受邀新用户和已有账户生成真实投递流程；对不能登录的输入返回同样的 `202`、不可预测流程 ID 和有效期格式，且该流程不能通过验证。流程 ID 绑定本次邮箱、邀请和 OTP，验证请求只提交流程 ID 与 OTP，不重新提交邮箱。

身份响应只包含终端需要的稳定字段：

```json
{
  "identity": {
    "user": "member-name",
    "label": "成员显示名"
  }
}
```

游客查询返回 `"identity": null`，不把未登录当作服务器错误。`AuthIdentity.user` 对应唯一登录名，`label` 对应显示名。接口不返回账户状态、邮箱、数据库 ID 或其他成员资料。

公开错误按流程阶段限定，不直接把内部失败原因作为机器码返回：

| 阶段 | 公开响应规则 |
| --- | --- |
| OTP 申请 | 语法有效且未触发限流的请求统一返回 `202`，提示“若符合登录条件，将收到验证码”；账户不存在、停用、邀请无效及单个邮箱投递失败不改变该结果 |
| OTP 验证 | 流程不存在、验证码错误或过期、邀请失效及账户不可用统一返回 `invalid_or_expired_code`，使用相同 HTTP 状态及提示；不公开 `invalid_invitation` 或 `account_disabled` |
| 请求校验与限流 | 可返回 `invalid_request` 或 `rate_limited`；语法校验和邮箱、来源地址计数不依赖账户是否存在，重试信息规则保持一致 |
| 全局服务故障 | 数据库或邮件服务整体不可用时可返回可重试的 `service_unavailable`，判定独立于目标邮箱，不把单个收件人的投递失败映射为全局故障 |
| 会话查询与注销 | 无会话或已失效会话分别返回空身份及幂等注销结果；网络和服务错误不得伪装为空身份或注销成功 |

响应检查同时覆盖 HTTP 状态、字段、有效期、重试信息和处理时间差异，不只比较 JSON 结构。具体错误、过期、停用、邀请及邮件投递原因只记录在受控日志中。门户把公开机器码映射为双语文案，终端不直接展示数据库、邮件服务商或网络堆栈错误。规则依据参考 [OWASP 认证指南](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html#authentication-and-error-messages)。

接口文档与实现同步维护。前端从同一响应定义映射 TypeScript 类型，不另写一份无校验的重复字段清单。

## 会话与请求安全

- 浏览器持有密码学随机会话凭证，数据库只保存其摘要。会话凭证不出现在 JSON、终端输出、URL 或日志中。
- Cookie 使用 `Secure`、`HttpOnly`、合适的 `SameSite` 和受限路径；正式环境不通过 JavaScript 读取会话。
- 会话采用明确的绝对有效期。注销、账户停用和管理员撤销后，`GET /auth/session` 必须返回空身份。
- 注销及其他已认证写请求要求跨站请求伪造防护。OTP 申请与验证通过同源检查、服务端流程 ID 和限流防止跨站提交及验证码猜测。
- OTP 使用安全随机源生成，只保存摘要，设置有效期、最大尝试次数、重发间隔及按邮箱和来源地址的限流。
- 邀请字符串和 OTP 按敏感输入处理，不进入命令历史、普通输入草稿、Transcript、分析事件或访问日志。
- 日志记录请求 ID、稳定错误码和必要安全事件，不记录 Cookie、邀请原文、OTP、邮件正文或完整敏感请求体。
- 数据库查询使用参数化语句。限流和账户状态判断在服务端执行，前端隐藏入口不构成授权。

## 终端接入

新增 HTTP 版 `AuthGateway` 适配器，复用[现有认证接口](../../../docs/architecture/terminal-extending.md#多步交互与登录)。Parser、命令注册与虚拟工作区的职责不变，`Session` 需要增加分步计时，见[登录超时与取消](#登录超时与取消)。

适配器放在 `app/features/terminal/client-auth.ts`，与 `client-session.ts` 同为模块级客户端组装，经 `app/components/home/HeroSection.vue` 的 `TerminalServices` 注入 `auth`。主题、语言与路由切换都不重建它。适配器不进入首页入场模块，入场编排不发起认证请求；终端不得依赖 `app/features/intro/`，该依赖会被 `scripts/source-analysis.ts` 的层间规则拒绝。

会话恢复与注销核对需要的待核对状态保存在适配器模块内，不放在组件或 composable 的局部状态里。组件卸载会丢弃局部状态，而核对要在下次挂载时继续。

`login` 的适配流程为：

1. 选择已有账户登录或邀请激活，再询问邮箱；邀请激活在独立敏感输入中提供邀请字符串。
2. 请求 OTP，并通过现有 `ctx.ask()` 的 `otp` 输入读取验证码。
3. 校验成功后返回 `AuthIdentity`，由现有命令调用 `ctx.setIdentity()`。
4. 失败时按[公开错误码到终端输出](#公开错误码到终端输出)返回已本地化的结果，不泄漏邮箱是否存在，不自动重复发送邮件。

`whoami` 继续通过 `getSession()` 查询真实身份。页面挂载后恢复有效会话，使刷新后的提示身份与 Cookie 一致；游客不额外显示错误。终端只存在于首页，恢复入口是 `HeroSection` 挂载与 `whoami`，其他页面不查询会话。请求必须传递 `AbortSignal`，组件卸载或新命令取消后不得写回旧身份。

`logout` 成功后才清除本地身份和输出。网络失败时不直接清除身份或宣称注销成功，按下文规则重新核对服务端会话。

### 公开错误码到终端输出

`Session` 对 `sensitive` 命令统一把异常映射为 `error.auth`，`login` 已标记为 sensitive。适配器若把 `invalid_or_expired_code`、`rate_limited`、`service_unavailable` 作为异常抛出，分阶段提示会退化为一条通用失败，与 HTTP 接口一节的错误规则冲突。预期失败由适配器返回已本地化的错误行并把命令状态记为失败，异常只用于程序缺陷与不可识别的情况；取消仍由 `AbortSignal` 判定，不经过该映射。

适配器需要翻译能力才能产出双语文案，而 `AuthGateway.login` 的上下文当前是 `Pick<CommandContext, "ask" | "write">`。1A 把它扩展为包含 `t` 的上下文，同步修改 `app/features/terminal/core/types.ts`、[终端扩展接口](../../../docs/architecture/terminal-extending.md#多步交互与登录)与 `core/extensions.test.ts`。命令行的历史记录规则不变：`login` 不写入历史与 Transcript。

### 登录超时与取消

当前 `TERMINAL.limits.commandTimeout` 为 30 秒，`Session.execute()` 从命令开始统一计时，包含 `ctx.ask()` 等待输入。接入前必须调整命令的超时策略，不能把收取验证码的人工等待压入同一个 30 秒期限，也不能直接放大所有命令的超时。

改动集中在 `app/features/terminal/config.ts` 的期限配置、`core/session.ts` 的计时与取消，以及 `core/session.test.ts` 的用例。命令通过可选元数据声明自己的期限，`Session` 在等待 `ctx.ask()` 时分段计时；Parser、命令注册与输出归属不变。放大全局期限会让其他命令在挂起时更久不返回，不能采用。

- 普通命令保留现有执行期限。登录分别设置网络请求超时、单步输入等待期限和流程总期限，等待输入不消耗网络请求时限。
- OTP 有效期由服务端执行，不因终端等待、暂停或切换页面延长。客户端在期限内允许取消，并提供明确的过期及重新发起提示，不自动重发邮件。
- Esc、Ctrl+C、超时或卸载取消本地等待和请求，并释放输入。取消后的旧命令不得追加输出或调用 `ctx.setIdentity()`。
- `AbortSignal` 取消浏览器等待不等于回滚服务端事务。验证或注销已经提交时，服务端会话可能与本地身份不同；不能承诺取消后账户未激活或会话未建立。
- 验证或注销请求取消、超时或响应丢失后，将本地认证结果标为待核对。当前有效的生命周期通过新的 `getSession()` 请求恢复身份；组件已卸载时，在下次挂载核对。恢复请求独立于旧命令，只更新身份，不重放欢迎输出、验证、投递或注销。服务端已提交但浏览器未收到会话 Cookie 时，查询仍返回游客，需要重新登录，不重试已消费的 OTP 或撤销已完成的邀请激活。
- 核对失败时保留待核对状态并显示可重试提示。原请求尚未完成时，一次查询不能视为最终结果；后续 `whoami`、新认证操作前或重新挂载时再次核对。恢复结果只能在对应生命周期和认证操作仍有效时应用，不能覆盖较新的登录或注销。

### 生命周期与文案

主题和语言切换不重建 Session，不改变门户会话。终端适配器只在客户端发起认证请求，SSR 不读取浏览器 Cookie 并共享可变认证状态。

双语新增文案遵循[翻译规则](../../../docs/terminology/translation.md)。现有文案在同一变更中改写，中英两份同步：

| 位置 | 当前内容 | 处理 |
| --- | --- | --- |
| `command.loginUnavailable` | 成员登录尚未开放 | 区分服务不可用与功能未开放，或移除 |
| `command.membersUnavailable` | `whoami` 游客分支输出“成员系统尚未开放” | 改为未登录提示，不再声称系统未开放 |
| `summary.login` | 帮助与 `man` 中显示“等待接入后端” | 改为成员登录入口 |

新增公开错误码 `invalid_or_expired_code`、`invalid_request`、`rate_limited`、`service_unavailable` 的双语文案，两份 locale 的 key 与插值保持一致，由 `app/i18n/i18n.test.ts` 校验。

术语先登记再使用。[术语表](../../../docs/terminology/terms.md)目前只有“会话”一条与认证相关，邀请、验证码、账户、统一身份认证与成员资格在写入文档和界面文案前先补表。

## 验证与验收

### Go 验证

- gofmt、go vet、staticcheck、`go test -race` 与生产构建全部通过。
- 迁移可以从空数据库执行，也可以重复运行到同一版本。
- 有效邀请能激活一次；过期、撤销、已使用和邮箱不匹配的邀请均被拒绝。
- 邀请预设登录名和显示名按规则写入账户，保留名称及并发登录名冲突均被拒绝。
- OTP 过期、错误、超过尝试次数、重放和并发验证均有确定结果。
- 未受邀邮箱不能激活账户，响应不暴露账户是否存在。
- 已有、未知、停用邮箱及无效邀请的公开响应遵守分阶段规则，覆盖单个邮箱投递失败、全局服务故障及按邮箱限流，比较 HTTP 状态、字段和处理时间差异。
- 会话刷新可恢复，注销和停用后失效，伪造或篡改会话凭证不能通过。
- 邮件投递失败或验证事务回滚时不建立账户或会话。验证事务提交后响应丢失、请求取消或客户端超时，账户和会话仍保持完整。查询结果以浏览器实际持有的有效 Cookie 为准，未收到 Cookie 时返回游客并允许重新登录，不将网络中断视为事务回滚。

### 门户验证

- 受邀用户可从 `login` 完成激活，随后 `whoami` 显示后端身份。
- 已有用户可登录、注销，刷新后有效会话仍能恢复。
- 无效邀请、错误 OTP、限流、服务不可用和请求取消均有中英文结果。
- 用户等待验证码超过 30 秒仍可在登录及 OTP 有效期内完成流程，普通命令保留执行期限；单步等待、网络请求及流程总期限分别覆盖超时和清理。
- 覆盖验证或注销提交前后取消、Cookie 设置后响应丢失、原请求晚于恢复查询完成、卸载后重新挂载及旧恢复请求晚于新认证操作返回，身份最终以当前服务端会话为准，不重放旧输出或副作用。
- 验证码错误、验证码过期、限流和服务不可用分别显示对应双语文案，不退化为通用认证失败。
- 认证 E2E 使用替身网关且不连接数据库；Go 集成测试单独运行，浏览器分片不启动 Go 服务与 PostgreSQL。
- 敏感输入不进入历史、草稿、Transcript 和日志。
- 主题与语言切换保留会话；终端展开、路由返回和减少动画行为不回归。
- 未登录访问现有公开页面不受影响，现有终端命令与虚拟工作区保持原行为。

门户继续执行 `bun run check` 与相关 `bun run test:e2e`。Go 检查以 `backend/` 中的单一入口（Makefile 或等价脚本）为准，本地与 CI 调用同一组命令，不以门户构建成功代替 Go 测试。测试邮件投递使用专用测试实现，真实服务商至少进行一次受控验收，不发送自动化批量邮件。

## 1B：Passkey

1B 复用 `users` 和 `sessions`，增加凭据表与四个独立接口：绑定选项、绑定验证、登录选项、登录验证。绑定必须要求有效会话和跨站请求伪造防护；登录成功前仍检查账户状态。

浏览器使用原生 Passkey 界面，终端只负责发起流程和显示结果。保存公钥、凭据 ID、用户句柄、签名计数及必要设备元数据，不保存私钥或可被当作私钥使用的材料。验证挑战短期有效且只能使用一次。

验收覆盖绑定、重新登录、撤销凭据、停用账户、挑战重放、取消浏览器弹层和多凭据账户。1B 不改变邀请激活方式，也不要求学校统一身份认证可用。

## 1C：学校统一身份认证

学校公开入口为 [西安财经大学统一身份认证](https://cas.xaufe.edu.cn/login)。公开页面可见账号登录和扫码登录，但票据校验端点、返回属性和应用接入要求尚未验证。

实施前取得以下学校侧条件：

- 门户回调地址完成应用注册和白名单配置。
- 确认使用 `/serviceValidate` 还是 `/p3/serviceValidate`。
- 确认稳定身份字段、可用属性和个人信息使用限制。
- 确认扫码登录也能完成标准服务票据流程。

Go 后端直接校验服务票据并核对 `service`，不接受前端提交的学号或姓名。学校身份通过独立外部身份表绑定到 `users`，邀请仍决定是否允许首次激活。服务票据不进入日志。

认证页优先使用新窗口，完成后由同源回调页通知原窗口重新查询会话，避免整页跳转丢失浏览器内存中的终端历史和草稿。通知只包含成功或失败，不包含会话凭证。门户注销默认只撤销门户会话，不主动退出全校统一身份认证。

学校侧条件未满足前，1C 保持未验证状态，不用模拟学校响应宣称接入完成。标准协议核对可参考 [Apereo CAS Protocol Specification](https://apereo.github.io/cas/development/protocol/CAS-Protocol-Specification)。
